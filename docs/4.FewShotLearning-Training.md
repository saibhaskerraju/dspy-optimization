# Few-Shot Learning: Traditional vs DSPy

## 1. Traditional few-shot approach and problems

- Manually curated few-shot examples live in prompts and are easy to copy incorrectly
- Static examples do not adapt to new data patterns or evolving product terminology
- Prompt drift over time as product language changes, pricing shifts, or policies change
- Hard to evaluate systematically across datasets without a clear metric or dev set
- Scaling requires constant manual updates across multiple prompts and services
- Inconsistent outputs when inputs are slightly different, ambiguous, or noisy
- No automated way to select best examples for a new task, segment, or locale
- Knowledge is trapped in prompt text, making reuse, ownership, and governance difficult
- Example quality depends on individual judgment, so teams converge slowly on best prompts
- Lack of versioning for prompts makes regressions hard to trace and fix

Example in this project:
If the prompt includes a few examples that label password-reset issues as
`General`, the model may misroute real technical incidents. The fix is manual:
edit the prompt, redeploy, and hope the change does not break other categories.

## 2. DSPy solution: training to solve few-shot problems

DSPy replaces manual prompt tinkering with a training loop that searches for
effective few-shot demonstrations based on a metric. This makes the process
repeatable and measurable instead of ad hoc. You define:

- A signature that describes inputs and outputs
- A module that runs the signature (e.g., `ChainOfThought`)
- A small training set with labeled examples that represent real cases
- A metric for correctness (exact match, business rules, or weighted rules)
- Optional constraints like confidence ranges or allowed labels
- A dev set for regression checks and comparison across runs

Then DSPy uses optimizers like `BootstrapFewShot` to select and refine
demonstrations. It searches for sets of examples that maximize the metric,
reducing reliance on manual guesswork. The result is a compiled program with
stable behavior that can be saved and reused without hand-editing the prompt.

Example in this project:
The training data includes billing, refund, technical, and general emails.
DSPy automatically picks the most useful demonstrations to improve routing
accuracy without manually rewriting the prompt.

## 3. DSPy usage: optimization to deployment (production and MLOps highlights)

- Train once, save the optimized program as JSON for reuse
- Load the JSON in a separate runtime for inference or serving
- Keep the same signature and module code between training and serving
- Version artifacts like models for reproducibility and auditability
- Swap datasets or metrics without rewriting prompts
- Enable quick regression checks by re-running metrics on a dev set
- Separate data curation from prompt logic so teams can iterate independently
- Promote to production by pinning a JSON artifact and rolling forward safely
- Roll back by restoring a prior JSON version without rewriting code

Example in this project:
The training script saves a JSON program artifact, and the usage script loads
that artifact to run inference with the same signature and module structure.
This mirrors a production workflow where training and serving are separated.

## 4. Key differences (Traditional vs DSPy)

| Aspect | Traditional few-shot | DSPy few-shot training |
| --- | --- | --- |
| Example selection | Manual and static | Optimized by metric | 
| Adaptation to new data | Manual prompt edits | Retrain or re-optimize | 
| Evaluation | Ad hoc and informal | Metric-driven and repeatable | 
| Reproducibility | Hard to trace | Saved program artifacts | 
| Production workflow | Prompt copy-paste | Train, save, load, infer |
| Maintenance effort | High | Lower over time |

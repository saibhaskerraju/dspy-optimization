## 1. Each AI Provider Demands a Different Approach

Prompt engineering looks simple until you switch models. Each provider has its own prompt format, preferred style, and hidden quirks. What works well for one model can fail on another, and small changes in phrasing can swing results dramatically.

### Examples of Major Model Providers

### OpenAI Models

**Required Style**: Conversational, natural-language instructions with clear role definitions.

**Official Documentation**: https://platform.openai.com/docs/guides/prompt-engineering

**Recommended Format**:
```markdown
You are an expert analyst. Please analyze the following document step by step:
1. Read the document carefully
2. Identify key points
3. Provide your reasoning
4. Give your final conclusion
Document: {content}
```
Key Requirements from Documentation:
- Use clear, conversational language.
- Provide step-by-step instructions.
- Define roles explicitly.
- Use examples for complex tasks.

### Azure OpenAI Models

**Required Style**: OpenAI-style prompts plus Azure deployment and versioning details.

**Official Documentation**: https://learn.microsoft.com/azure/ai-services/openai/concepts/prompt-engineering

**Recommended Format**:
```markdown
You are an expert analyst. Please analyze the following document step by step:
1. Read the document carefully
2. Identify key points
3. Provide your reasoning
4. Give your final conclusion
Document: {content}
```
Key Requirements from Documentation:
- Use your deployment name instead of a model name.
- Set the correct API version for each request.
- Keep role separation consistent (system/user/assistant).
- Validate responses against expected output fields.

### Anthropic Models

**Required Style**: Explicit task/context separation (often with XML-style tags) to guide long inputs.

**Official Documentation**: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/overview 

**Recommended Format**:
```markdown
You are a careful assistant.
<task>Summarize the text</task>
<context>...</context>
```
Key Requirements from Documentation:
- Separate task, context, and constraints with clear delimiters.
- Put the task first and keep instructions brief and concrete.
- Use consistent labels or tags for long inputs.
- Ask for the exact output shape you need.

### Google Models

**Required Style**: Clear goals, specific instructions, and enough context to steer the response.

**Official Documentation**: https://cloud.google.com/discover/what-is-prompt-engineering#prompt-engineering-overview-and-guide

**Recommended Format**:
```markdown
Goal: Summarize the document for a business audience.
Context: The audience cares about risks, timeline, and budget impact.
Instructions: Return 3 bullets with one sentence each.
Document: {content}
```
Key Requirements from Documentation:
- Set a clear goal and desired output format.
- Provide relevant context or background.
- Be specific and break complex tasks into steps.
- Use examples or few-shot prompts when accuracy matters.

### The Business Problem: Maintenance Nightmare

For the same task (summarize, classify, extract), the work multiplies as you add vendors.

#### What multiplies per vendor

- **Prompting**: Different roles, templates, and input conventions mean the same task needs multiple prompt variants.
- **Parsing**: Response shapes, tool call formats, and error patterns vary, so you maintain separate parsers and fallbacks.
- **Testing**: Benchmarks and edge cases differ by provider, forcing duplicate evaluation and regression suites.
- **Process**: Teams must track multiple docs, updates, and best practices to keep prompts stable over time.

### How DSPy Fixes the Maintenance Nightmare

- **Prompting**: Define tasks as typed DSPy modules; the framework adapts prompts per model so you write the task once.
- **Parsing**: Use structured signatures and adapters so outputs map to a consistent schema across vendors.
- **Testing**: Build evals once and re-run them on any model to compare quality and catch regressions.
- **Process**: Versioned programs, reusable datasets, and optimization runs replace manual prompt rewrites.

## 2. Imperative Programming vs Declarative Programming

Traditional prompt engineering is imperative: you write exact instructions step by step and hope the model follows them. DSPy is declarative: you define the task as input/output signatures and let the framework compile the best prompt strategy.

### Imperative (Prompt-Only)

You hard-code the procedure in the prompt, which is brittle across models.

```markdown
You are an expert analyst. Please analyze the following document step by step:
1. Read the document carefully
2. Identify key points
3. Provide your reasoning
4. Give your final conclusion
Document: {content}
```

### Declarative (DSPy)

You specify what the program should do, not how to phrase it.

```python
import dspy

class Summarize(dspy.Signature):
	"""Summarize a document for a business audience."""

	document: str = dspy.InputField()
	summary: str = dspy.OutputField()

summarizer = dspy.Predict(Summarize)
result = summarizer(document=content)
print(result.summary)
```

### Why This Solves the Maintenance Problem

- **Prompting**: The signature stays the same even if you change models.
- **Parsing**: Outputs map to named fields like `summary`, so you avoid ad-hoc parsing.
- **Testing**: You can evaluate the `Summarize` module with a single eval harness.
- **Process**: Optimization runs update prompts without rewriting the signature.

### Key Advantages of Declarative Signatures

1. **Intent Over Implementation**
	- Signature: "Return reasoning, answer, and confidence from a document and question."
	- Manual: "Here is exactly how you should think, format, and respond."
	- Focus on what you want, not how to phrase it.

2. **Self-Documenting Code**
	- Signatures make inputs and outputs explicit in the class definition.
	- Manual prompts hide intent inside long strings.
	- Types and field names make validation clearer.

3. **Composability and Reuse**
	- Signatures can be extended, inherited, and composed into pipelines.
	- Manual prompts are monolithic and hard to reuse.
	- Encourages an object-oriented approach to AI programs.

4. **Maintainability**
	- Add or remove fields without rewriting large prompt blocks.
	- Reduce parsing breakage when requirements change.
	- Version-control friendly diffs.

5. **Team Productivity**
	- Any developer can read and modify a signature quickly.
	- Less reliance on prompt-engineering specialists.
	- Clear separation between task definition and optimization.
